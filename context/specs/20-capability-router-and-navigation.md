# Spec 20 — Capability router: preventive health, healthcare preparation, service navigation

## Status: COMPLETE — implemented and verified live against the real Supabase/OpenAI backend (2026-08-28).

Written and implemented in the same session, on the project owner's explicit "audit first, then proceed with implementation unless there is a serious architectural blocker" instruction — the drafted-then-wait-for-a-separate-"implement"-instruction pattern Specs 17–19 used doesn't apply here; this spec file documents what was built, not a proposal awaiting approval.

## Goal

Evolve Beca from a narrow topic-based Health Education chatbot into a capability-based assistant that also handles **Preventive Health Guidance**, **Healthcare Preparation**, and **Healthcare Service Navigation** — without regressing Health Education or weakening the existing safety layer (Specs 06/17).

## Depends on

Specs 05, 06, 17, 19 (`app/api/chat/route.ts`, `lib/ai/*`, `lib/directory/lookup.ts`, `lib/kb/search.ts`) — all read, none of their existing logic altered except where explicitly noted below (the `EscalationResponseSchema`-building code was extracted into a shared helper, `buildEscalationResponse`, with identical behavior — see Decision 5).

## Architecture decisions

1. **Capability router runs strictly after the existing safety branch's fallthrough point.** `classifyCapability()` (`lib/ai/classify-capability.ts`) is called only once the deterministic red-flag check and the AI urgency classifier (unmodified) have both already cleared a message as not urgent and not needing clarification. This is a routing/topic classifier, never a second safety mechanism — Part 4 of the task: "do not make this classifier the sole safety mechanism."

2. **Capability enum includes `"emergency"` as a defense-in-depth backstop, not a rival safety path.** If this second, independently-reasoning classifier flags `emergency` on a message the primary layer already cleared, the route escalates using the *exact same* `buildEscalationResponse()` helper and fixed copy the primary layer uses — never new safety copy, never a second escalation mechanism. Severity defaults to `medium` unless the classifier's own `risk_level` is `high`. This only ever adds an escalation the primary layer missed; it can never suppress one the primary layer already caught (the primary check runs unconditionally, first, and returns before capability classification is ever reached).

3. **`preventive_health` is a real, distinct label at the routing/classification level, sharing retrieval mechanics with `health_education`.** Both currently dispatch through the same, unmodified `searchKb`/`generateAnswer` RAG pipeline — deliberately, to protect the already-verified Health Education path from any regression risk (the task's explicit "do NOT regress Health Education" instruction). `disease_information`, `when_to_seek_care`, `medication_safety`, and `out_of_scope` share the same pipeline for the same reason. This is a stated, defensible scoping choice (see `lib/ai/schema.ts`'s `RAG_CAPABILITIES` comment), not a hidden shortcut — most of the KB's existing `intents`/`example_questions` metadata already covers prevention-flavored questions on the same underlying topics.

4. **`healthcare_preparation` uses a new, deterministic, non-vector-RAG lookup** (`preparation_checklists` table, `lib/preparation/lookup.ts`) keyed by an exact `service` enum match (`PREPARATION_SERVICES`, 10 values) — never similarity search, per the task's explicit "should NOT depend entirely on vector RAG." When a checklist is found, it is fed to the **existing, unmodified** `generateAnswer()` as the sole retrieved chunk — reusing the already-proven faithfulness/citation/simple-Pidgin generation contract instead of inventing a second one, while guaranteeing the model has nothing else to draw from. No matching service (or a generation failure) falls through to the standard RAG flow, where the pre-existing internally-authored `clinic-appointment-prep` KB topic (#12) still covers general preparation guidance as a safety net — never a hard failure.
   - Every checklist's `clinical_review_status` is `"drafted_pending_clinical_review"` — Claude-drafted, not reviewed by a clinician. The citation label is `"Beca — preparation guide"`, deliberately **not** `"clinically reviewed"`, so the UI never claims a review pass that hasn't happened. Flagged in `progress-tracker.md` Open Questions, same standard already applied to the un-reviewed Pidgin refusal copy (Spec 09).

5. **`service_navigation` is entirely deterministic — no LLM call at all.** `directory_entries` gained a `services text[]` column (additive, alongside the existing escalation `category` column — not a replacement) so a facility can be found by a general, non-emergency service (`NAVIGATION_SERVICES`, 14 values) independent of its escalation-routing category. `lib/directory/lookup.ts`'s new `findByService()` queries it; the response (`ServiceNavigationResponseSchema`, a new discriminated-union member alongside `ChatResponseSchema`/`EscalationResponseSchema`/`ClarificationResponseSchema`) is built entirely from that query's result. A genuine zero-match result is returned honestly (`matched_entries: []` plus a plain "not on file" message) — never a fallback to RAG or LLM invention, per the task's explicit "never hallucinate a facility."
   - `services` values on the 11 real seed entries are **inferred from each entry's existing `category`, not independently verified per facility** — flagged in `data/clinic_directory.json` entry #12's own note, the same cautious treatment already applied to unconfirmed contact numbers via the `verified` field. No new facility data source was added — `SCOPE.md` explicitly locks the seed directory as the only clinic/service data source, and that lock was not overridden.

6. **New response shape required a new discriminant field on the three existing shapes.** `service_navigation: z.literal(false)` was added to `ChatResponseSchema`, `EscalationResponseSchema`, and `ClarificationResponseSchema` (mirroring exactly how Spec 17 added `needs_clarification: false` to the two shapes that predated it) so `ChatThread.tsx`'s discriminant chain (`escalated` → `needs_clarification` → `service_navigation` → default) type-checks and narrows correctly. All object-literal construction sites (`lib/ai/client.ts`, `app/api/chat/route.ts`) were updated to set it.

7. **KB expansion: 7 new topics (22–28), all with live-verified WHO URLs** (`WebFetch`-confirmed before being committed, same standard the 2026-08-27 audit's KB expansion used) — oral health, food safety, cholera, hepatitis B, STIs, healthy ageing, newborn care. Closes several of the Part 5 gaps (general health, NCD, communicable disease, child health, sexual/reproductive health buckets). Topics 1–21 are completely untouched. A `capabilities` metadata field was added to the schema (optional, defaulting to `[]`) and populated on the 7 new topics only — validated by `scripts/ingest-kb.ts` but **not persisted to `kb_sources` or used by retrieval**, the same "validated but not yet load-bearing" treatment the 2026-08-27 audit already gave `intents`/`keywords`/`example_questions` before Spec 19 made `keywords` load-bearing. Retrofitting `capabilities` onto the original 21 topics was deliberately not done this pass (no functional payoff yet, since retrieval doesn't filter on it — see Decision 3) — flagged as a clean follow-up, not silently skipped.
   - **Known, honest gap, not fixed this pass:** no `sleep` or `hydration` topic exists. A candidate CDC sleep source returned HTTP 403 during live verification; `hydration` was already flagged as a distinct, uncovered topic during the 2026-08-27 audit (topic #8 explicitly does not cover it). Both are reflected as `should_answer: false` entries in `evaluation/health_education.json` with an honest note, not silently dropped from the eval set.

8. **Two new evaluation-support scripts, not merged into existing ones.** `evaluation/{health_education,preventive_health,healthcare_preparation,service_navigation,safety}.json` (20 items each, Part 17) and `tests/run-capability-eval.ts` (Part 18/19) are new and separate from `tests/test-queries.json`/`tests/run-test-set.ts` — the two check different things (existing safety/grounding regression vs. the newer capability router), matching `ai-workflow-rules.md`'s own splitting rule. `tests/run-test-set.ts` is unmodified and was re-run against this build with **zero regression: 100.0% overall (20/20), 100.0% escalated (7/7)**.

## Out of scope (explicitly, not overlooked)

- **Conversation memory / follow-up-question resolution** (Part 16 of the task) — the app remains fully stateless per turn, as it has been since Spec 17 Decision 1. Threading conversation history into `searchKb`/`generateAnswer` would touch the already-verified Health Education generation path, which the task explicitly says not to regress. Logged as a real, deliberate gap in `progress-tracker.md` Open Questions, not silently omitted.
- **Geographic/location-based filtering for service navigation** — the capability classifier captures a free-form `location` field, but `findByService()` does not yet filter by it (the seed directory has no lat/long or LGA data to filter against — Part 11's fuller facility schema, with geocoding, was evaluated and not built: it would require inventing facility data this project's locked scope forbids, per `SCOPE.md`).
- **Reranking, capability-aware retrieval filtering on `kb_sources`, and a labeled precision/recall threshold-tuning pass** (Parts 7/9) — evaluated per the task's own "evaluate, don't blindly implement" framing; not built, to avoid touching the retrieval internals Spec 19 already tuned and verified, for capabilities where a routing-level distinction was sufficient.
- **Facility administrator/self-serve update flow, facility verification lifecycle timestamps beyond the existing `verified` field** (Part 12) — no change to the seed-directory model this pass, consistent with not inventing a new facility data source.
